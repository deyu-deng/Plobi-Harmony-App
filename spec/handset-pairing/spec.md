# Feature Specification: 设备配对与设备面切换（WP-APP-HANDSET）

**Created**: 2026-10-07  
**Status**: Draft  
**Input**: User description: "把 App 从旧的 /api/agenda/* + 手填令牌 切换到设备面：/api/handset/* 路径 + 6 位配对码换设备令牌；同时清理上次体检发现的小瑕疵。"

## Overview

本 App（Plobi 鸿蒙平板端）当前所有请求仍打桌面看板的旧路径 `/api/agenda/*`，鉴权用手填的会话令牌——而桌面侧按裁定 64/68 已改为设备面专用前缀 `/api/handset/*` + 一机一令牌，且旧 `app_token` 已整体退役。结果是：**App 现在进门必 401，完全连不上现役桌面**。

本功能把 App 接上设备面：① 请求路径全部切到 `/api/handset/*`；② 新增配对流程（桌面开 6 位码 → 用户敲码 → 换回本机专属设备令牌）；③ 每个请求自动带设备令牌；④ 设置页移除已无用的手填令牌入口。同时按用户确认，把上次代码体检发现的工程小瑕疵（死代码、重复样板、魔法字符串、标签不一致等）一并清理。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 敲码配对，换回设备令牌 (Priority: P1)

用户在桌面 Plobi 上点「新码」得到一个 6 位数字码，在平板 App 的设置页填入桌面地址和这个码（可选填设备名），点「配对」。App 调用配对接口换回本机专属设备令牌并保存；设置页显示「已配对」状态（设备名）。

**Why this priority**: 配对是设备面唯一进门通道（裁定 68 后没有回退路）。没有这一步，后面所有功能都 401。

**Independent Test**: 可以单独验证——填码点配对后，设置页出现已配对状态，且本机 Preferences 中出现设备令牌。

**Acceptance Scenarios**:

1. **Given** 桌面已开出一个有效 6 位码，**When** 用户填入正确码点「配对」，**Then** 配对成功，设置页显示已配对（含设备名），令牌存入本地
2. **Given** 码已过期 / 已被用过 / 输错，**When** 用户点「配对」，**Then** 提示「码错或已过期，回桌面重新开一个码」，不进入已配对状态
3. **Given** 用户连续输错 5 次触发桌面配对锁（HTTP 429 + Retry-After），**When** 再次点「配对」，**Then** 按提示照 Retry-After 显示锁定时长（约 1 小时），且 App 不自动重试
4. **Given** 设备名输入框留空，**When** 配对成功，**Then** 上报桌面的设备名为默认「Plobi 平板」；**Given** 填了设备名，**Then** 上报所填名字（最长 64 字，超长不允许提交）
5. **Given** 码不是 6 位数字，**When** 点「配对」，**Then** 不发请求，直接提示格式不对

---

### User Story 2 - 配对后拉到清单 (Priority: P1)

配对成功后，用户回主页点「刷新」，App 用设备令牌从设备面拉今日/明日/待确认三段数据并正常渲染（含离线缓存路径不变）。

**Why this priority**: 这是「App 能用」的核心价值——清单是本 App 的第一功能。

**Independent Test**: 在已修好 401 根因的现役桌面局域网内，配对后点刷新能看到真实数据。

**Acceptance Scenarios**:

1. **Given** 已配对且桌面在线，**When** 用户点「刷新」，**Then** 今日/明日/待确认三段渲染出设备面返回的数据，路径全部走设备面前缀
2. **Given** 已配对但桌面离线，**When** 点「刷新」，**Then** 沿用现有离线降级（显示缓存 + 上次同步时间 + 连接错误分类提示）
3. **Given** 未配对（本地无设备令牌），**When** 点「刷新」，**Then** 提示「请先在设置里配对」，不发起设备面请求

---

### User Story 3 - 批待确认 (Priority: P2)

在待确认列表点「确认 / 忽略」，App 用设备令牌调设备面的裁定接口，成功后条目从列表移除（响应可能是 `{deleted:true}`）。

**Why this priority**: 批待确认是看板闭环的另一半，依赖清单先可用。

**Independent Test**: 配对后对待确认条目点确认/忽略，桌面侧状态变化且条目消失。

**Acceptance Scenarios**:

1. **Given** 已配对且存在待确认条目，**When** 点「确认」，**Then** 调用设备面 confirm 接口成功，条目从待确认列表移除
2. **Given** 已配对且存在待确认条目，**When** 点「忽略」，**Then** 调用设备面 dismiss 接口成功（兼容 `{deleted:true}` 响应），条目移除
3. **Given** 接口返回失败，**When** 裁定请求完成，**Then** 沿用现有错误横幅提示，条目保留

---

### User Story 4 - 令牌失效引导重新配对 (Priority: P2)

桌面撤销本机设备后，App 下一次请求会收到鉴权失败；WS 握手被拒（HTTP 403）。此时 App 要给出「重新配对」的明确指引，而不是含糊的网络错误。

**Why this priority**: 一机一令牌的必然运维路径；引导不清用户会以为 App 坏了。

**Independent Test**: 在桌面撤销设备后刷新，页面出现引导重新配对的提示。

**Acceptance Scenarios**:

1. **Given** 已配对但令牌被桌面撤销，**When** 点「刷新」，**Then** 提示令牌失效、引导去设置页重新配对
2. **Given** 已配对但令牌被撤销，**When** 发送聊天（WS 握手被 403 拒），**Then** 提示指向重新配对或通道未开，不显示为裸网络错误

---

### User Story 5 - 聊天预切设备面 (Priority: P3)

聊天页拉总秘书列表的请求预切到设备面前缀。桌面侧还没给设备钥匙开这个口子（交接规格 §8 契约未定），所以切换后短期表现为「找不到总秘书」的既有提示；等桌面开口子后无需再改 App。

**Why this priority**: 用户已确认预切，但它不阻塞主线功能；桌面侧口子落地前聊天本来就不通。

**Independent Test**: 代码中 agents 请求路径为设备面前缀；桌面未开口子时聊天页显示既有「通道未开」提示。

**Acceptance Scenarios**:

1. **Given** 已配对，**When** 进入聊天页，**Then** 拉总秘书列表的请求走设备面前缀 + 设备令牌
2. **Given** 桌面侧口子未开，**When** 请求失败，**Then** 显示既有「电脑端还没打开平板对话通道」类提示（不新增契约猜测）

---

### User Story 6 - 工程清理 (Priority: P3)

按用户确认纳入本次：清除上次体检发现的死代码与不一致，巩固工程卫生。

**Why this priority**: 不影响功能但防止认知腐化；与功能切片同批交付，一次干净。

**Independent Test**: 构建通过、ArkTS 严格检查 0 违规、既有单测全绿；抽查项（无未使用导出、共享常量单点定义）通过。

**Acceptance Scenarios**:

1. **Given** 清理完成，**When** 运行静态检查与构建，**Then** 0 违规、构建成功
2. **Given** 事件卡片与时间线展示同类条目，**When** 对比两处 kind 标签，**Then** 使用同一份中文标签映射（不再一处英文一处中文）
3. **Given** 全仓检索令牌请求头常量，**When** 统计定义点，**Then** 只有单点定义
4. **Given** 构建 profile，**When** 检查 SDK 版本声明，**Then** 显式配置了 targetSdkVersion（消除构建警告）

### Edge Cases

- 配对接口返回 200 但响应体缺 `token` 字段 → 视为配对失败，提示重试，不落半截状态
- 用户清了 App 数据（令牌丢失）→ 视为未配对；没有「找回」，只能重新配对（令牌只在配对响应里出现一次）
- 配对成功后用户改了桌面地址 → 已存令牌对新地址无效，首次请求 401 后走重新配对引导
- 6 位码输入含非数字字符 → 前端直接拦截不发请求
- 已配对状态下再次进入设置页 → 显示已配对状态与设备名，并允许「解除配对」（清除本机令牌回到未配对态）
- WS 握手能否带自定义头在真机上尚未验证（README 待办）→ 桌面撤销或通道未开时提示文案需覆盖两种可能

## Requirements *(mandatory)*

### Functional Requirements

**设备面切换**
- **FR-001**: 所有日程类请求 MUST 走设备面前缀路径：清单查询、待确认查询、单日快照、确认、忽略五类接口逐一对应切换，不再请求旧看板路径
- **FR-002**: 所有设备面请求 MUST 在请求头携带本机设备令牌（沿用现有令牌头名），桌面地址仍由用户在设置页填写
- **FR-003**: 聊天页拉总秘书列表 MUST 预切到设备面前缀（用户已确认；桌面侧口子未开前允许失败并显示既有提示）

**配对**
- **FR-004**: 设置页 MUST 提供配对入口：桌面地址 + 6 位数字配对码 + 可选设备名 + 「配对」动作；设备名留空时上报默认「Plobi 平板」，最长 64 字
- **FR-005**: 配对请求 MUST 是设备面唯一免凭证调用，请求体为 `{code, deviceName}` 形状，成功响应中的 `deviceId` 与 `token` MUST 持久化到本地
- **FR-006**: 配对失败分支 MUST 分开提示：码错/过期/已用（401）→ 引导回桌面重开码；连错锁定（429 + Retry-After）→ 按响应头显示等待时长，且锁定期间 MUST NOT 自动重试
- **FR-007**: 设置页 MUST 移除手填令牌输入框（裁定 68 后无可用手填令牌）；配对成功后显示已配对状态（含设备名）
- **FR-008**: 已配对状态 MUST 提供「解除配对」动作：清除本机令牌与配对信息，回到未配对态

**失效引导**
- **FR-009**: 设备令牌被撤销/失效时（HTTP 401/403），相关页面 MUST 显示「令牌失效，请到设置页重新配对」类指引，不显示裸状态码
- **FR-010**: WS 聊天握手被拒（升级失败 403 或关闭）MUST 归入「令牌失效或通道未开」的既有提示口径

**工程清理（用户已确认纳入）**
- **FR-011**: MUST 清除死代码：无调用者的导出与未使用的导入（含 ChatSession 的对象转换辅助、AppConfig 接口、事件 kind 常量表中未接线部分、页面内未使用的令牌头常量与日期函数导入）
- **FR-012**: 时间格式化与补零辅助 MUST 收敛到既有工具模块单点复用；两份 API 客户端的公共样板（请求头构造、尾部斜杠处理、失败分类入口、响应头读取）MUST 收敛为共享实现；令牌请求头常量 MUST 单点定义
- **FR-013**: 事件 kind 的中文标签映射 MUST 全仓统一为一份（卡片与时间线同源），拼写错误常量名 MUST 修正
- **FR-014**: 本地写入的 API 版本号键名 MUST 纳入统一常量管理（消除裸字符串键）
- **FR-015**: 构建 profile MUST 显式声明 targetSdkVersion，消除构建警告
- **FR-016**: 提醒重排中的不可达分支（对已入选事件的重复推导）MUST 移除，行为不变

### Key Entities *(include if feature involves data)*

- **设备令牌（DeviceToken）**: 配对成功后由桌面签发的一机专属凭证；含设备标识与令牌本体；仅在本机持久化，丢失只能重新配对
- **配对码（PairCode）**: 桌面生成的 6 位数字码，5 分钟有效、一次性；是设备面唯一免凭证入口的凭据
- **设备名（DeviceName）**: 上报给桌面、显示在桌面设备列表的本机称呼，≤64 字，默认「Plobi 平板」
- **配对响应（RedeemResponse）**: 配对成功响应，含 `deviceId`、`token`、`scopes`；令牌仅在此响应中出现一次

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 配对流程（填码 → 点配对 → 见到已配对状态）在 1 分钟内可完成
- **SC-002**: 配对成功后，在已修好 401 根因的现役桌面局域网内点「刷新」，今日/明日/待确认三段全部渲染真实数据
- **SC-003**: 全部鉴权失败场景（码错、锁定、令牌撤销、WS 被拒）都有明确中文行动指引，无裸 HTTP 码暴露给用户
- **SC-004**: 交付时构建成功、ArkTS 严格检查 0 违规、既有单测全绿，且新增配对/路径逻辑有对应单测
- **SC-005**: 工程清理验收抽查全部通过：无未使用导出残留、令牌头常量单点、kind 标签全仓一份、无构建警告 targetSdkVersion

## Assumptions

- 桌面侧已按裁定 64/68 完成设备面改造且 401 根因已修复（README 记录 2026-10-04 实测通过）；本仓只做 App 侧对齐
- 配对契约以 README 转述的交接规格为准：`POST /api/handset/pair/redeem`，请求体 `{code, deviceName}`，成功响应 `{deviceId, token, scopes}`；401/429 语义如上文
- 设备令牌沿用现有本地存储位置与请求头名（`X-Plobi-Session-Token`），令牌值从「手填」变为「配对签发」，其余链路（含 WS 头注入方式）不变
- 令牌与配对信息继续只存本机 Preferences，不入日志、不入 URL（既有纪律保持）
- 聊天桌面侧口子（设备钥匙可访问的 agents 端点）由桌面仓负责，契约落地前 App 侧按「通道未开」提示，不猜新契约
- 「解除配对」仅清除本机令牌；桌面侧设备列表的撤销/删除由桌面管理，不在本仓范围
- 单测保持纯逻辑风格（不依赖真机/网络），配对与路径逻辑以纯函数方式可测

## Open Questions

- WS 握手在真机上能否携带自定义请求头尚未实测（README 待办）；若真机不支持，需改为桌面提供的一次性票据 URL 方案——本次先按现状（带头发起）实现，真机验证后如需调整另开任务
- 配对锁定（429）时长的本地提示精度：照 `Retry-After` 原值显示（秒/分钟自适应），若桌面实际不返回该头则显示通用「约 1 小时」——以桌面实测为准
